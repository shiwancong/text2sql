## 语义理解框架（核心）

### ⚠️ 核心原则：SQL必须直接反映用户输入

**最重要的规则**：生成的SQL必须使用用户输入的**原始内容**作为查询参数，而不是内部转换后的ID或编码值。

```
用户输入："电子电气工程学院"
✅ 正确：WHERE d.NAME_ LIKE '%电子电气工程学院%'
❌ 错误：WHERE d.DEPT_ID = '10035'  -- 硬编码的ID，用户看不懂

用户输入："李德声"
✅ 正确：WHERE t.NAME_ = '李德声'
❌ 错误：WHERE t.TEA_NO = '11140'  -- 硬编码的工号

用户输入："2022级"
✅ 正确：WHERE s.ENROLL_YEAR = '2022'
❌ 错误：WHERE s.GRADE_ID = '202201'  -- 硬编码的年级ID
```

**为什么这样要求？**
1. **可读性**：SQL直接反映用户的查询意图
2. **可移植性**：SQL可以在其他环境直接执行
3. **可维护性**：用户能理解SQL在查什么
4. **可验证性**：用户能看到自己的输入如何被使用

**内部处理 vs 外部SQL：**
```
内部处理（用户看不到）：
1. 用户输入："电子电气工程学院"
2. 系统内部可能先查询：SELECT ID FROM HQ_CODE_DEPT WHERE NAME_ LIKE '%电子电气工程学院%'
3. 得到结果：'10035'

外部SQL（给用户的）：
✅ 直接使用用户输入：
   SELECT m.NAME_ AS 专业名称
   FROM HQ_CODE_MAJOR m
   WHERE m.DEPT_ID IN (SELECT ID FROM HQ_CODE_DEPT WHERE NAME_ LIKE '%电子电气工程学院%')
     AND m.ISTRUE = 1

❌ 不要使用硬编码ID：
   SELECT m.NAME_ AS 专业名称
   FROM HQ_CODE_MAJOR m
   WHERE m.DEPT_ID = '10035'  -- 用户不知道这是什么
     AND m.ISTRUE = 1
```

**例外情况**：
- 用户明确提供了代码/ID（如"查询代码Z35BZ95202的课程"）
- JOIN的关联条件（ON子句）可以使用ID，但WHERE条件仍用名称

#### 2.1.1 学年格式理解（🔥 极重要！）

⚠️ **核心概念**：数据库中学年格式为"YYYY-YYYY"，不是单独的年份

```
┌─────────────────────────────────────────────────────────────┐
│                     学年格式说明                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   正确格式：                                                 │
│   ├── "2023-2024" 表示 2023-2024 学年                       │
│   ├── "2022-2023" 表示 2022-2023 学年                       │
│   └── SCHOOL_YEAR 字段存储的就是这种格式                    │
│                                                             │
│   用户问题 "2023年开设课程多少门" 的理解：                   │
│   ├── 错误理解：WHERE SCHOOL_YEAR = '2023' ❌               │
│   ├── 正确理解：需要查询包含2023自然年的学年                 │
│   │   └── 2022-2023-02（2023上半年）+ 2023-2024-01（2023下半年）│
│                                                             │
│   解决方案：                                                 │
│   ├── 方式1：通过 HQ_CODE_XNXQ 表匹配自然年范围              │
│   │   WHERE SCHOOL_YEAR IN (                                 │
│   │     SELECT DISTINCT SCHOOL_YEAR                          │
│   │     FROM HQ_CODE_XNXQ                                   │
│   │     WHERE TO_NUMBER(SUBSTR(BEGIN_DATE, 1, 4)) <= 2023   │
│   │       AND TO_NUMBER(SUBSTR(END_DATE, 1, 4)) >= 2023     │
│   │   )                                                      │
│   ├── 方式2：明确指定两个学期                                 │
│   │   WHERE (SCHOOL_YEAR = '2022-2023' AND TERM_CODE = '02')│
│   │     OR (SCHOOL_YEAR = '2023-2024' AND TERM_CODE = '01') │
│   └── 方式3：从 HQ_JX_MAJOR_COURSE 表查询（YEAR_ 字段是自然年）│
│       WHERE YEAR_ = 2023                                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**学年相关字段对比**：

| 字段名 | 表名 | 格式 | 说明 |
|--------|------|------|------|
| SCHOOL_YEAR | HQ_JX_KCB, HQ_JX_JXZ | "2023-2024" | 学年格式 |
| YEAR_ | HQ_JX_MAJOR_COURSE | 2023 | 自然年格式 |
| ENROLL_YEAR | HQ_XS_STU | "2024" | 入学年份（字符串） |
| ENROLL_GRADE | HQ_XS_STU | "2024" | 入学年级（字符串）⚠️ |

**错误案例**：
```sql
-- ❌ 错误：学年格式错误
WHERE SCHOOL_YEAR = '2023'  -- 不存在这样的学年

-- ✅ 正确：使用完整学年格式
WHERE SCHOOL_YEAR = '2023-2024'

-- ❌ 错误：使用了错误的字段
WHERE ENROLL_YEAR = '2024'  -- 应该用 ENROLL_GRADE

-- ✅ 正确：使用 ENROLL_GRADE 查询入学年级
WHERE ENROLL_GRADE = '2024'
```

#### 2.2.1 荣誉/成果表区分（🔥 极重要！）

⚠️ **核心概念**：有三个不同的表存储荣誉/成果相关数据，用途不同

```
┌─────────────────────────────────────────────────────────────┐
│                   荣誉/成果表区分                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   1. HQ_RS_TEACH_RES（教学成果奖）                          │
│   ├── 用途：教学成果奖项（教师为主）                         │
│   ├── 关键字段：JX_NAME(奖项名称)、DATE_(获奖时间)          │
│   ├── 关联表：HQ_RS_TEACH_RES_CY（参与人员）               │
│   └── 场景："教学成果奖"、"教学成果类奖项"                   │
│                                                             │
│   2. HQ_RS_HONOR_RES（个人/团队荣誉成果）                   │
│   ├── 用途：教职工个人或团队获得的荣誉                       │
│   ├── 关键字段：JX_NAME(荣誉名称)、DATE_(获奖时间)          │
│   ├── 关联：通过 DEPT_ID 关联到部门                         │
│   └── 场景："护理学院的荣誉成果"、"某年获取的荣誉"           │
│                                                             │
│   3. HQ_JC_XX_RY（学校荣誉/学校级别荣誉）                   │

│   ├── 关键字段：XXRY_GRADE_CODE(等级：1=国家级)             │
│   ├── 关键字段：IS_TASK_THE_HEAD(是否牵头单位：1=是)         │
│   └── 场景："作为牵头单位获得的国家级荣誉"                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**表名选择决策表**：

| 用户问题 | 正确表名 | 错误表名 | 关键条件 |
|---------|---------|---------|---------|
| "教学成果奖" | HQ_RS_TEACH_RES | HQ_RS_HONOR_RES ❌ | JX_NAME, DATE_ |
| "教学成果类奖项最多的是哪一年" | HQ_RS_TEACH_RES | HQ_RS_HONOR_RES ❌ | SUBSTR(DATE_,1,4) |
| "某年某学院获取的荣誉成果" | HQ_RS_HONOR_RES | HQ_RS_TEACH_RES ❌ | JOIN HQ_CODE_DEPT |
| "作为牵头单位获得的国家级荣誉" | HQ_JC_XX_RY | HQ_RS_HONOR_RES ❌ | XXRY_GRADE_CODE='1', IS_TASK_THE_HEAD=1 |

**错误案例对比**：
```sql
-- ❌ 错误：查询"作为牵头单位获得的国家级荣誉"用了错误的表
SELECT * FROM HQ_RS_HONOR_RES
WHERE HONOR_RES_ID = '010103'  -- 这个表和字段都不对

-- ✅ 正确：使用 HQ_JC_XX_RY 表
SELECT TITLE, DETAILS, YEAR_MONTH
FROM HQ_JC_XX_RY
WHERE XXRY_GRADE_CODE = '1'      -- 国家级
  AND IS_TASK_THE_HEAD = 1        -- 牵头单位
ORDER BY YEAR_MONTH DESC

-- ❌ 错误：查询"教学成果奖"用了错误的字段
SELECT r.NAME_, r.DATE_
FROM HQ_RS_TEACH_RES r
-- NAME_ 字段不存在！

-- ✅ 正确：使用 JX_NAME 字段
SELECT r.JX_NAME, r.DATE_
FROM HQ_RS_TEACH_RES r
WHERE SUBSTR(r.DATE_, 1, 4) = '2024'
```

#### 2.2.1 班级类型判断规则（重要！）

⚠️ **核心概念**：教学班 ≠ 行政班

```
┌─────────────────────────────────────────────────────────────┐
│                   班级类型区分                               │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   教学班 (Teaching Class)                                   │
│   ├── 用途：上课、排课的基本单位                            │
│   ├── 表：HQ_JX_KCB.TEACHCLASS_NAME                         │
│   ├── 特点：一个教学班 = 一门课的上课单位                   │
│   └── 示例："2022大数据与财务管理P01班（高数）"              │
│                                                             │
│   行政班 (Administrative Class)                              │
│   ├── 用途：学生管理、学籍管理的单位                        │
│   ├── 表：HQ_CODE_CLASSES                                   │
│   ├── 特点：一个行政班 = 一个固定学生群体                   │
│   └── 示例："2022大数据与财务管理P01班"                      │
│                                                             │
│   关系：                                                    │
│   └── 一个教学班可能包含多个行政班（合班上课）              │
│       或 一个行政班可能分为多个教学班（分班上课）            │
└─────────────────────────────────────────────────────────────┘
```

**班级类型判断决策表：**

| 用户问题关键词 | 班级类型 | 应使用的表/字段 | 是否关联行政班表 |
|--------------|---------|----------------|----------------|
| "上课班级"、"排课"、"课表" | 教学班 | `HQ_JX_KCB.TEACHCLASS_NAME` | ❌ 不需要 |
| "某教室的课"、"某日的课" | 教学班 | `HQ_JX_KCB.TEACHCLASS_NAME` | ❌ 不需要 |
| "班级人数"、"班级学生" | 行政班 | `HQ_CODE_CLASSES` | ✅ 需要 |
| "属于哪个专业" | 行政班 | `HQ_CODE_CLASSES` | ✅ 需要 |
| "辅导员"、"班长" | 行政班 | `HQ_CODE_CLASSES` | ✅ 需要 |
| "高教了哪些班" | 教学班 | `HQ_JX_KCB_TEA` → `HQ_JX_KCB` | ❌ 不需要 |

**典型场景对比：**

```
场景1：查询排课信息（使用教学班）
用户问题："1号教学楼211室2024-05-17的上课班级"
→ 使用 HQ_JX_KCB.TEACHCLASS_NAME
→ 不关联 HQ_CODE_CLASSES
→ 结果显示：教学班名称

场景2：查询班级学生信息（使用行政班）
用户问题："2022大数据P02班有多少学生"
→ 关联 HQ_CODE_CLASSES
→ 使用 c.CLASS_ID 或 c.NO_ 关联学生表
→ 结果显示：行政班的学生人数

场景3：查询教师教的班级（使用教学班）
用户问题："高雯萱教了哪些班"
→ 使用 HQ_JX_KCB.TEACHCLASS_NAME
→ 不关联 HQ_CODE_CLASSES
→ 结果显示：教学班名称
```

**错误示例（必须避免）：**

```
❌ 错误：查询排课时关联了行政班表
SELECT c.NAME_ AS 班级, cr.NAME_ AS 课程
FROM HQ_JX_KCB k
JOIN HQ_JX_TEACHCLASS_XZB tx ON k.TEACHCLASS_ID = tx.TEACHCLASS_ID
JOIN HQ_CODE_CLASSES c ON tx.CLASS_ID = c.NO_  ← 多余关联！
WHERE k.CLASSROOM_ID = 'xxx'
问题：一个教学班对应多个行政班时，结果会爆炸

✅ 正确：直接使用课表中的教学班
SELECT k.TEACHCLASS_NAME AS 班级, cr.NAME_ AS 课程
FROM HQ_JX_KCB k
WHERE k.CLASSROOM_ID = 'xxx'
直接显示 k.TEACHCLASS_NAME，不关联行政班表
```

#### 2.3 隐含条件判断规则（核心！）

| 用户问题语义 | 隐含条件 | 自动添加的WHERE条件 | 理由 |
|-------------|---------|-------------------|------|
| "专业有几个" | 当前有效 | `ISTRUE = 1` | 用户问"有"是指当前存在的 |
| "开设哪些专业" | 当前开设 | `ISTRUE = 1` | "开设"暗示当前有效 |
| "学院有哪些" | 当前存在 | `ISTRUE = 1` | 用户想看当前的学院列表 |
| "教师人数" | 在职教师 | `IS_NORMAL = 1` | "教师"默认指在职的 |
| "教职工比例" | 在职教职工 | `IS_NORMAL = 1` | 比例计算基于在职人员 |
| "学生人数" | 在校学生 | `STU_STATE_CODE = '01'` | "学生"默认指在校的 |
| **"学籍异动学生"** | 历史记录 | **不加ISTRUE** | 异动是历史事件 |
| **"办理休学"** | 历史记录 | **不加ISTRUE** | 休学是历史变更 |
| **"获奖历史"** | 历史记录 | **不加ISTRUE** | 获奖是历史事件 |
| "退学学生" | 历史记录 | 不加ISTRUE | 退学是历史状态 |

### 步骤3：字段选择语义规则

#### 3.1 名称匹配 vs 代码匹配

```
用户输入："电子电气工程学院"（完整名称）
→ 使用 NAME_ 字段：WHERE NAME_ LIKE '%电子电气工程学院%'

用户输入："Z35BZ95202"（明确代码）
→ 使用 CODE_ 字段：WHERE CODE_ = 'Z35BZ95202'

用户输入："2022级"（年级信息）
→ 使用 ENROLL_YEAR 字段：WHERE ENROLL_YEAR = '2022'
```

#### 3.2 关联字段选择规则

```
场景：关联班级表
→ 检查关联字段类型
  - 如果是 CLASS_ID（字符串）→ 关联 NO_
  - 如果是 CLASS_ID（数值）→ 关联 ID
  - 使用 describe_table 确认字段类型

场景：关联院系表
→ 使用 ID 字段关联（标准）
```

### 步骤4：语义理解示例

#### 示例1：理解"开设"的语义

```
用户问题："电子电气工程学院开设有哪些专业？"

语义分析：
├─ "开设" → 暗示当前有效的专业
├─ "电子电气工程学院" → 部门名称
├─ "专业" → HQ_CODE_MAJOR 表
└─ 推断条件：
    ├─ 必须添加：m.ISTRUE = 1（"开设"=有效）
    └─ 关联条件：d.NAME_ LIKE '%电子电气工程学院%'

生成SQL：
SELECT m.NAME_ AS 专业名称
FROM HQ_CODE_MAJOR m
WHERE m.DEPT_ID = (SELECT ID FROM HQ_CODE_DEPT WHERE NAME_ LIKE '%电子电气工程学院%')
  AND m.ISTRUE = 1  ← "开设"的语义隐含
```

#### 示例2：理解"教职工"的语义

```
用户问题："查询我校少数民族教职工人数及所占比例"

语义分析：
├─ "教职工" → 暗示在职人员
├─ "少数民族" → NATION_CODE != '01'
├─ "比例" → 需要计算百分比
└─ 推断条件：
    ├─ 必须添加：IS_NORMAL = 1（"教职工"=在职）
    └─ 使用 COUNT(*)（而非 COUNT()）

生成SQL：
SELECT
    COUNT(CASE WHEN NATION_CODE != '01' THEN 1 END) AS 少数民族人数,
    COUNT(*) AS 总人数,
    ...
FROM HQ_RS_TEA
WHERE IS_NORMAL = 1  ← "教职工"的语义隐含
```

#### 示例3：理解"学籍异动"的语义

```
用户问题："2024级计算机专业学籍异动学生有几人"

语义分析：
├─ "学籍异动" → 历史变更记录，非当前状态
├─ "2024级" → ENROLL_YEAR = '2024'
├─ "计算机专业" → MAJOR_CODE 关联
└─ 推断条件：
    ├─ 不添加 ISTRUE（异动是历史记录）
    ├─ 不添加 STU_STATE_CODE（已异动的学生不在校）
    └─ 使用 COUNT(DISTINCT STU_NO) 去重

生成SQL：
SELECT COUNT(DISTINCT c.STU_NO)
FROM HQ_XS_CHANGE c
JOIN HQ_XS_STU s ON c.STU_NO = s.STU_NO
WHERE s.ENROLL_YEAR = '2024'
  -- 注意：不加 ISTRUE，因为异动记录是历史数据
```

#### 示例4：理解"连续三年"的语义

```
用户问题："连续三年获得教学成果奖项的二级学院有哪些？"

语义分析：
├─ "连续三年" → 需要LAG窗口函数判断连续性
├─ "二级学院" → LEVEL_TYPE = 'YX'
├─ "教学成果奖项" → HQ_RS_TEACH_RES 表
└─ 推断条件：
    ├─ 必须使用 LAG() 判断年份连续性
    ├─ 不加 ISTRUE（获奖是历史记录）
    └─ 添加 LEVEL_TYPE = 'YX'

生成SQL：
WITH ranked_data AS (
  SELECT ...
    LAG(...) OVER (...) AS 前一年
  FROM HQ_RS_TEACH_RES r
  WHERE r.LEVEL_TYPE = 'YX'  ← "二级学院"的语义
    -- 注意：不加 ISTRUE，历史获奖记录
)
...
```

### 准确率第一
- 每次查询前进行**多重验证**
- 不确定的字段名必须先查看表结构
- SQL 执行后检查结果合理性
- 空结果需要分析原因并调整查询


### 步骤4详解：字段理解与业务判断

这是**最关键**的步骤，决定SQL是否准确：

```
4.1 获取字段详情
   ├─ 使用 describe_table 查看所有字段
   ├─ 重点关注：字段名、类型、注释
   └─ 识别关键字段：ISTRUE、IS_NORMAL、状态码、标志位

4.2 基于语义理解自动判断条件（新增！）
   │
   ├─ 判断1：用户问题是否隐含"当前有效"？
   │  └─ 关键词：有、几个、哪些、开设、现有...
   │     → 自动添加 ISTRUE = 1
   │
   ├─ 判断2：用户问题是否隐含"在职/在校"？
   │  └─ 关键词：教师、教职工、学生...
   │     → 自动添加 IS_NORMAL = 1 或 STU_STATE_CODE = '01'
   │
   ├─ 判断3：用户问题是否关于"历史事件/变更"？
   │  └─ 关键词：异动、休学、退学、获奖、历史、曾经...
   │     → 不添加 ISTRUE（历史记录不需要有效性检查）
   │
   ├─ 判断4：用户问题是否涉及"连续性"？
   │  └─ 关键词：连续N年、连续N学期...
   │     → 使用 LAG 窗口函数
   │
   └─ 判断5：用户问题是否包含"绝对日期"？
      └─ 关键词：2024-05-17、具体日期...
         → 使用 HQ_JX_JXZ_DAY 表转换

4.3 字段业务含义对照表
   ├─ ISTRUE = 1 → 有效数据（专业、课程、部门等）
   ├─ ISTRUE = 0 → 无效/已停用数据
   ├─ IS_NORMAL = 1 → 在职教职工
   ├─ STU_STATE_CODE = '01' → 在校学生
   ├─ STU_STATE_CODE = '03' → 退学学生
   ├─ STU_CHANGE_CODE = '11' → 休学
   ├─ STU_CHANGE_CODE = '03' → 退学
   └─ XXX_CODE → 代码字段，可能需要关联代码表

4.4 条件添加决策表（基于语义）

┌─────────────────────┬──────────────────┬─────────────────────────┐
│ 用户问题语义         │ 隐含条件          │ SQL实现                │
├─────────────────────┼──────────────────┼─────────────────────────┤
│ "有几个/哪些"       │ 当前有效          │ ISTRUE = 1             │
│ "开设/现有"         │ 当前有效          │ ISTRUE = 1             │
│ "教师/教职工"       │ 在职              │ IS_NORMAL = 1          │
│ "学生/在校生"       │ 在校              │ STU_STATE_CODE = '01'  │
│ "学籍异动"          │ 历史变更          │ 不加ISTRUE             │
│ "办理休学"          │ 历史事件          │ 不加ISTRUE             │
│ "获奖/荣誉"         │ 历史记录          │ 不加ISTRUE             │
│ "连续N年"           │ 连续性判断        │ LAG窗口函数           │
│ "具体日期(2024-xx)" │ 日期转换          │ HQ_JX_JXZ_DAY表        │
└─────────────────────┴──────────────────┴─────────────────────────┘

4.5 检查清单
   ├─ [ ] 主表是否需要 ISTRUE = 1？（基于"当前有效"语义判断）
   ├─ [ ] 子查询/关联表是否需要 ISTRUE = 1？
   ├─ [ ] 教师表是否需要 IS_NORMAL = 1？（基于"在职"语义判断）
   ├─ [ ] 学生表是否需要 STU_STATE_CODE = '01'？
   ├─ [ ] 历史记录表是否不加 ISTRUE？（基于"历史事件"判断）
   ├─ [ ] 是否有其他状态字段需要过滤？
   ├─ [ ] 用户问题是否隐含了状态条件？
   └─ [ ] 查询结果是否符合业务常识？
```

## 关键处理规则

### 规则1：表名必须验证
```
❌ 错误：直接使用用户输入的表名
✅ 正确：
   1. 先使用 RAG 检索相关表
   2. 使用 describe_table 确认表存在
   3. 确认字段名后再生成 SQL
```

### 规则1.5：SQL必须直接反映用户输入（禁止使用硬编码ID）

⚠️ **重要原则**：详见上文"⚠️ 核心原则：SQL必须直接反映用户输入"

**快速参考：**

| 用户问题 | ❌ 错误（硬编码ID） | ✅ 正确（使用用户输入） |
|---------|-------------------|---------------------|
| 建工院有哪些教研室？ | `WHERE DEPT_ID = '10035'` | `WHERE d.NAME_ LIKE '%建工%'` |
| 李德声老师的电话？ | `WHERE TEA_NO = '11140'` | `WHERE NAME_ = '李德声'` |
| 陶瓷琉璃艺术系有哪些专业？ | `WHERE DEPT_ID = '10047'` | `WHERE d.NAME_ LIKE '%陶瓷琉璃%'` |

**记住：**
- WHERE条件中始终使用用户输入的名称/关键词
- JOIN的ON子句可以使用ID进行关联
- 如果用户明确提供了代码/ID，则直接使用

### 规则2：代码字段关联（禁止硬编码CASE WHEN）

⚠️ **极重要**：当查询包含代码字段（XXX_CODE）需要显示名称时，必须关联代码表，禁止使用硬编码的CASE WHEN

```
❌ 错误：使用硬编码的CASE WHEN
SELECT
  s.NATION_CODE AS 民族代码,
  CASE s.NATION_CODE
    WHEN '01' THEN '汉族'
    WHEN '03' THEN '回族'
    WHEN '05' THEN '苗族'
    ELSE s.NATION_CODE
  END AS 民族名称
FROM HQ_XS_STU s
问题：
- 硬编码了民族映射关系
- 新增民族需要修改SQL
- 不符合"避免硬编码"原则
- 可维护性差

✅ 正确：关联代码表获取名称
SELECT
  s.NATION_CODE AS 民族代码,
  c.NAME_ AS 民族名称
FROM HQ_XS_STU s
JOIN HQ_CODE c ON c.CODE_ = s.NATION_CODE
WHERE c.CODE_TYPE = 'NATION'  -- 或使用 GROUP_TYPE
优势：
- 自动从代码表获取最新数据
- 新增民族无需修改SQL
- 符合语义理解框架
- 可维护性好
```

**常见代码字段关联规则：**

| 代码字段 | 代码类型 | 关联条件示例 |
|---------|---------|--------------|
| NATION_CODE | 民族代码 | `WHERE c.CODE_TYPE = 'NATION'` |
| SEX_CODE | 性别代码 | `WHERE c.CODE_TYPE = 'SEX'` |
| STU_STATE_CODE | 学籍状态代码 | `WHERE c.CODE_TYPE = 'STU_STATE'` |
| PYCC_CODE | 培养层次代码 | `WHERE c.CODE_TYPE = 'PYCC'` |
| TERM_CODE | 学期代码 | `WHERE c.CODE_TYPE = 'TERM'` |
| COURSE_TYPE_CODE | 课程类型代码 | `WHERE c.CODE_TYPE = 'COURSE_TYPE'` |

### 规则2.1：禁止硬编码规则（核心！）

⚠️ **最重要**：SQL中禁止出现任何硬编码的业务数据、代码值、状态值

```
┌─────────────────────────────────────────────────────────────┐
│                  什么是硬编码？                              │
├─────────────────────────────────────────────────────────────┤
│ 硬编码 = 在SQL中直接写入具体的业务数据、代码值           │
│                                                             │
│ ❌ 硬编码示例：                                            │
│   - WHERE NATION_CODE = '01'    -- 硬编码汉族代码           │
│   - WHERE STU_STATE_CODE = '01' -- 硬编码在校状态          │
│   - WHERE c.CODE_TYPE = 'NATION' -- 硬编码代码类型          │
│   - CASE WHEN sex = '1' THEN '男'  -- 硬编码性别映射        │
│   - WHERE IS_SSJS = 1            -- 硬编码双师型标志        │
│                                                             │
│ ✅ 允许的示例：                                            │
│   - WHERE NAME_ = '李德声'       -- 用户输入，不是硬编码     │
│   - WHERE SCHOOL_YEAR = '2023-2024' -- 用户问题中提取      │
│   - SYSDATE, 'YYYY'               -- Oracle函数，不是业务数据│
└─────────────────────────────────────────────────────────────┘
```

**常见硬编码错误及解决方案：**

| 硬编码类型 | ❌ 错误示例 | ✅ 正确解决方案 |
|-----------|-----------|--------------|
| **民族代码** | `WHERE NATION_CODE != '01'` | 先查汉族代码，再用子查询：`WHERE NATION_CODE != (SELECT MAX(CODE_) FROM HQ_CODE WHERE CODE_TYPE = 'NATION' AND NAME_ LIKE '%汉族%')` |
| **性别代码** | `CASE WHEN SEX_CODE = '1' THEN '男'` | 关联代码表：`JOIN HQ_CODE c ON c.CODE_ = s.SEX_CODE WHERE c.CODE_TYPE = 'SEX'` |
| **学籍状态代码** | `WHERE STU_STATE_CODE = '01'` | 先查'01'对应的名称：`WHERE STU_STATE_CODE IN (SELECT CODE_ FROM HQ_CODE WHERE NAME_ = '在校')` |
| **学期代码** | `WHERE c.CODE_TYPE = 'TERM'` | 通过代码表动态筛选：`WHERE c.CODE_TYPE IN (SELECT DISTINCT CODE_TYPE FROM HQ_CODE WHERE NAME_ LIKE '%学期%')` |
| **状态标志** | `WHERE IS_SSJS = 1` | 从数据字典或业务注释中理解含义，必要时用CASE转换显示 |

**代码类型的动态获取示例：**

```sql
-- ❌ 错误：硬编码代码类型
WHERE c.CODE_TYPE = 'NATION'

-- ✅ 正确：动态确定代码类型
WHERE c.CODE_TYPE IN (
  SELECT DISTINCT CODE_TYPE
  FROM HQ_CODE
  WHERE CODE_TYPE IS NOT NULL
    AND ROWNUM <= 10  -- 先检查有哪些代码类型
)
AND c.CODE_ = main_table.NATION_CODE
```

**状态值判断的正确做法：**

```sql
-- ❌ 错误：硬编码状态值
WHERE STU_STATE_CODE = '01'  -- 假设'01'是在校

-- ✅ 正确：通过代码表确定
WHERE STU_STATE_CODE IN (
  SELECT CODE_ FROM HQ_CODE WHERE NAME_ = '在校' AND CODE_TYPE = 'STU_STATE'
)

-- 或者：如果业务规则明确，可以用注释说明
WHERE STU_STATE_CODE = '01'  -- '01'表示在校，根据业务规则
```

**什么时候可以硬编码？**

```
✅ 可以硬编码的情况：
1. Oracle函数和常量：SYSDATE, 'YYYY', 'MM', ROWNUM
2. 明确的数字运算：+ 1, - 5, * 100.0
3. 用户明确提供的值：WHERE NAME_ = '李德声'
4. 空字符串判断：WHERE XXX IS NOT NULL, XXX <> ''
5. 逻辑标志：IS_SSJS = 1（这是布尔值，不是硬编码业务数据）

❌ 不能硬编码的情况：
1. 业务代码值：NATION_CODE = '01', SEX_CODE = '1'
2. 状态代码值：STU_STATE_CODE = '01'
3. 代码类型值：CODE_TYPE = 'NATION'
4. 任何可能变化的业务数据
```

### 规则3：布尔值转换
```
IS_XXX 类字段（1/0）：
- 查询时：转换为 WHERE IS_XXX = 1/0
- 显示时：使用 CASE 转换为 是/否
```

### 规则4：精确匹配优先
```
⚠️ 重要：当用户指定了明确的实体名称时，必须使用精确匹配

❌ 错误：把完整名称拆分成多个 OR 条件
   WHERE NAME_ LIKE '%线控底盘%' OR NAME_ LIKE '%底盘%' OR NAME_ LIKE '%实训%'

✅ 正确：使用完整名称进行精确匹配
   WHERE NAME_ = '线控底盘实训室'
   或 WHERE NAME_ LIKE '%线控底盘实训室%'

判断标准：
- 用户输入的是完整实体名称（如"线控底盘实训室"、"李德声"）→ 精确匹配
- 用户输入的是描述性词汇（如"实训室"、"教师"）→ 模糊匹配
- 用户输入的是类别/范围（如"新能源汽车相关的"）→ 适当模糊匹配
```

### 规则5：ISTRUE有效性检查（必须）

⚠️ **极重要**：所有查询都必须检查 ISTRUE 字段，确保只查询有效数据

```
❌ 错误：没有检查ISTRUE
SELECT COUNT(*) FROM HQ_CODE_MAJOR

❌ 错误：只检查了主表的ISTRUE
SELECT COUNT(*) FROM HQ_CODE_MAJOR m WHERE m.ISTRUE = 1
AND NOT EXISTS (SELECT 1 FROM HQ_CODE_MAJOR_MAPPER mp WHERE mp.MAJOR_CODE = m.CODE_)

✅ 正确：所有表都检查ISTRUE
SELECT COUNT(*) FROM HQ_CODE_MAJOR m WHERE m.ISTRUE = 1
AND NOT EXISTS (
    SELECT 1 FROM HQ_CODE_MAJOR_MAPPER mp
    WHERE mp.MAJOR_CODE = m.CODE_ AND mp.ISTRUE = 1
)
```

**ISTRUE字段含义**：
- 1 = 有效/启用
- 0 = 无效/停用

**适用范围**：
- 几乎所有业务表都有ISTRUE字段
- 查询时必须加上 `ISTRUE = 1` 条件
- 多表关联时，每个表都要检查ISTRUE

**常见示例**：
```sql
-- 专业查询
```

### 规则5.2：连续性判断（使用LAG窗口函数）

⚠️ **重要**：当题目要求"连续N年/连续N学期"时，必须使用LAG窗口函数判断连续性

```
❌ 错误：只统计不同年份/学期数量，未判断连续性
SELECT d.NAME_ AS 学院名称
FROM HQ_RS_TEACH_RES r
JOIN HQ_CODE_DEPT d ON r.DEPT_ID = d.ID
GROUP BY d.NAME_
HAVING COUNT(DISTINCT SUBSTR(r.DATE_, 1, 4)) >= 3

✅ 正确：使用LAG判断年份连续性
WITH ranked_data AS (
  SELECT
    d.NAME_ AS 学院名称,
    SUBSTR(r.DATE_, 1, 4) AS 年份,
    LAG(SUBSTR(r.DATE_, 1, 4), 1) OVER (PARTITION BY d.ID ORDER BY SUBSTR(r.DATE_, 1, 4)) AS 前一年,
    LAG(SUBSTR(r.DATE_, 1, 4), 2) OVER (PARTITION BY d.ID ORDER BY SUBSTR(r.DATE_, 1, 4)) AS 前两年
  FROM HQ_RS_TEACH_RES r
  JOIN HQ_CODE_DEPT d ON r.DEPT_ID = d.ID
  WHERE d.LEVEL_TYPE = 'YX'  -- 二级学院筛选
    AND r.DATE_ IS NOT NULL
)
SELECT DISTINCT 学院名称
FROM ranked_data
WHERE TO_NUMBER(年份) - TO_NUMBER(前一年) = 1
  AND TO_NUMBER(前一年) - TO_NUMBER(前两年) = 1
```

**连续性判断的关键点**：
1. 使用 LAG() 窗口函数获取前N个时间点的值
2. 判断相邻时间点差值 = 1（年份）或连续（学期）
3. 对于学期：需要判断学年+学期的组合连续性
4. 确保按正确的分组（PARTITION BY）和排序（ORDER BY）

## Oracle 语法规范

### 大小写
```
✅ 表名和字段名大写：SELECT NAME_ FROM HQ_RS_TEA
✅ 字符串用单引号：WHERE NAME_ LIKE '%孙%'
❌ 字符串用双引号：WHERE NAME_ LIKE "%孙%"
```

### 分页（🔥 禁止使用FETCH FIRST）
```
⚠️ 该Oracle版本不支持 FETCH FIRST 语法（绝对禁止！）

❌ 错误：FETCH FIRST 3 ROWS ONLY
❌ 错误：FETCH FIRST 5 ROWS ONLY
❌ 错误：FETCH FIRST 1 ROW ONLY

✅ 正确：WHERE ROWNUM <= 3
✅ 正确：WHERE ROWNUM = 1 (单条)
✅ 正确（子查询方式）：
   SELECT * FROM (
     SELECT ... ORDER BY ...
   ) WHERE ROWNUM <= 3

❌ LIMIT n (MySQL语法)
```

### WEEKS 字段的特殊处理（🔥 极重要！）
```
⚠️ 课表中的 WEEKS 字段存储的是周次范围字符串，如："1-5,10-15,20"
⚠️ 不能使用等号精确匹配，必须使用 LIKE 模糊匹配或 JOIN 方式

❌ 错误：WHERE k.WEEKS = (SELECT WEEK FROM HQ_JX_JXZ_DAY WHERE DATE_ = '2024-05-17')
   -- 如果WEEKS="1-5,10-15"，此查询会失败

✅ 正确方式1：使用 LIKE 模糊匹配
   WHERE k.WEEKS LIKE '%' || (SELECT WEEK FROM HQ_JX_JXZ_DAY WHERE DATE_ = '2024-05-17') || '%'

✅ 正确方式2：使用 JOIN HQ_JX_JXZ_DAY 关联查询（推荐）
   JOIN HQ_JX_JXZ_DAY d ON k.WEEKS LIKE '%' || d.WEEK || '%'
   WHERE d.DATE_ = '2024-05-17'

✅ 正确方式3：使用 INSTR 函数
   WHERE INSTR(k.WEEKS, (SELECT WEEK FROM HQ_JX_JXZ_DAY WHERE DATE_ = '2024-05-17')) > 0
```

**典型场景**：
```sql
-- 场景1：查询某日期某教室的排课信息
SELECT k.TEACHCLASS_NAME, k.COURSE_CODE, k.PERIOD, t.NAME_
FROM HQ_JX_KCB k
JOIN HQ_JC_JS_ZZJG r ON k.CLASSROOM_ID = r.ID
JOIN HQ_JX_JXZ_DAY d ON k.WEEKS LIKE '%' || d.WEEK || '%'
LEFT JOIN HQ_JX_KCB_TEA kt ON k.ID = kt.KCB_ID
LEFT JOIN HQ_RS_TEA t ON kt.TEA_NO = t.TEA_NO
WHERE r.NAME_ = '1号教学楼211室'
  AND d.DATE_ = '2024-05-17'
  AND k.DAY_OF_WEEK = d.DAY_OF_WEEK
```

```
✅ SYSDATE
✅ TO_DATE('2024-01-01', 'YYYY-MM-DD')
✅ date BETWEEN ... AND ...

⚠️ 日期到周次/星期的转换：
```

### COUNT 语法（必须使用 COUNT(*)）
```
❌ 错误：COUNT() - 空括号是错误的
❌ 错误：COUNT - 没有括号是错误的

✅ 正确：COUNT(*) - 统计所有行
✅ 正确：COUNT(字段名) - 统计非空值
✅ 正确：COUNT(DISTINCT 字段名) - 统计去重后的行数

⚠️ 常见错误场景：
   - 计算比例时：SUM(CASE WHEN condition THEN 1 END) * 100.0 / COUNT(*)
   - 分组统计时：GROUP BY 后使用 COUNT(*) 而不是 COUNT()
```

```
├─ 如果3个教师×3门课→9条，但关联后变成50条？
└─ 如果预期3条，实际20+？→ 说明有关联问题

解决方法：
├─ 使用DISTINCT去重（治标）
├─ 只关联必要的表（治本）
└─ 优先显示代码字段，而非关联名称表
```
