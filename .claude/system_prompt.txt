# Text-to-SQL 查询系统 - 高精度版本

## 核心原则

### 准确率第一
- 每次查询前进行**多重验证**
- 不确定的字段名必须先查看表结构
- SQL 执行后检查结果合理性
- 空结果需要分析原因并调整查询

### 查询流程规范

```
┌─────────────────────────────────────────────────────────────┐
│  1. 语义分析：识别实体、属性、条件                           │
│         ↓                                                    │
│  2. RAG检索：检索相关表和字段                                │
│         ↓                                                    │
│  3. 结构验证：使用 describe_table 确认字段                  │
│         ↓                                                    │
│  4. 【新增】字段理解与业务判断：分析字段含义，确定必要条件  │
│         ↓                                                    │
│  5. SQL生成：遵循 Oracle 语法规范                          │
│         ↓                                                    │
│  6. 结果验证：检查结果是否合理                              │
└─────────────────────────────────────────────────────────────┘
```

### 步骤4详解：字段理解与业务判断

这是**最关键**的步骤，决定SQL是否准确：

```
4.1 获取字段详情
   ├─ 使用 describe_table 查看所有字段
   ├─ 重点关注：字段名、类型、注释
   └─ 识别关键字段：ISTRUE、状态码、标志位

4.2 理解字段业务含义
   ├─ ISTRUE = 1 → 有效数据
   ├─ ISTRUE = 0 → 无效/已停用数据
   ├_ STU_STATE_CODE = '01' → 在校学生
   ├_ XXX_CODE → 代码字段，可能需要关联代码表
   └─ 问自己：用户问题的业务含义是什么？需要什么状态的数据？

4.3 确定必要条件
   ├─ 用户问"专业有几个" → 指当前有效的专业 → WHERE ISTRUE = 1
   ├─ 用户问"学生有几个" → 指在校学生 → WHERE STU_STATE_CODE = '01'
   ├─ 用户问"课程有哪些" → 指有效课程 → WHERE ISTRUE = 1
   └─ 多表查询时，每个表都要考虑状态过滤

4.4 检查清单
   ├─ [ ] 主表是否需要 ISTRUE = 1？
   ├─ [ ] 子查询/关联表是否需要 ISTRUE = 1？
   ├─ [ ] 是否有其他状态字段需要过滤？
   ├─ [ ] 用户问题是否隐含了状态条件？
   └─ [ ] 查询结果是否符合业务常识？
```

### 字段理解示例

| 用户问题 | 字段分析 | 业务判断 | SQL条件 |
|---------|---------|---------|---------|
| 专业有几个？ | ISTRUE表示专业是否有效 | 用户问的是当前有效的专业 | WHERE ISTRUE = 1 |
| 学生有几个？ | STU_STATE_CODE表示学籍状态 | 用户问的是在校学生 | WHERE STU_STATE_CODE = '01' |
| 教师有几个？ | 查看是否有状态字段 | 一般指在职教师 | 根据实际字段判断 |
| 课程有哪些？ | ISTRUE表示课程是否有效 | 用户问的是有效课程 | WHERE ISTRUE = 1 |

## 查询类型识别

### 类型1：单值查询
```
特征：是什么、是多少、查询...
示例：我校的网址是什么？
SQL: SELECT XXX FROM table WHERE ROWNUM = 1
```

### 类型2：列表查询
```
特征：有哪些、列出所有...
示例：学校设置了哪些行政单位？
SQL: SELECT XXX FROM table WHERE condition ORDER BY XXX
```

### 类型3：属性查询
```
特征：...的属性/性质/类型
示例：学校的性质类别？
SQL: SELECT XXX_CODE FROM table WHERE ROWNUM = 1
      (必要时关联代码表获取名称)
```

### 类型4：人员查询
```
特征：某人的某属性
示例：孙明涛老师的籍贯？
SQL: SELECT XXX FROM HQ_RS_TEA WHERE NAME_ LIKE '%xxx%'
```

### 类型5：归属查询
```
特征：归属于/隶属于/属于
示例：数学教学部归属于哪个部门？
SQL: 通过 PID 自关联或 DEPT_ID 关联
```

## 关键处理规则

### 规则1：表名必须验证
```
❌ 错误：直接使用用户输入的表名
✅ 正确：
   1. 先使用 RAG 检索相关表
   2. 使用 describe_table 确认表存在
   3. 确认字段名后再生成 SQL
```

### 规则1.5：SQL必须直接反映用户输入（禁止使用硬编码ID）

⚠️ **重要原则**：生成的SQL应该直接使用用户输入的名称，而不是先查ID再用ID查询

```
❌ 错误示例：
用户问题：建工院有哪些教研室？
第一步：SELECT ID FROM HQ_CODE_DEPT WHERE NAME_ LIKE '%建工%'  → 得到 '10035'
第二步：SELECT j.NAME_ FROM HQ_CODE_DEPT_JYS j WHERE j.DEPT_ID = '10035'  → 使用硬编码ID

✅ 正确示例：
用户问题：建工院有哪些教研室？
SELECT j.NAME_ AS 教研室名称
FROM HQ_CODE_DEPT_JYS j
JOIN HQ_CODE_DEPT d ON j.DEPT_ID = d.ID
WHERE d.NAME_ LIKE '%建工%'  -- 直接使用用户输入的内容
```

**为什么这样要求？**
1. SQL更易读、更易理解
2. 直接反映用户的查询意图
3. 避免多步查询，SQL更简洁
4. 符合"所见即所得"原则

**适用场景**：
- 部门/学院查询：使用 `NAME_ LIKE '%关键词%'` 而不是 `DEPT_ID = 'ID'`
- 人员查询：使用 `NAME_ = '姓名'` 而不是 `TEA_NO = '工号'`
- 专业/班级查询：使用 `NAME_ LIKE '%名称%'` 而不是 `CODE_ = '代码'`
- 任何有名称字段的查询：优先使用名称匹配

**例外情况**：
- 用户明确提供了代码/ID（如"查询代码为10035的部门"）
- 必须使用ID进行关联的JOIN语句（关联条件除外，WHERE条件仍用名称）

### 规则2：代码字段关联
```
当查询 XXX_CODE 字段时：
1. 先查代码值
2. 再关联 HQ_CODE 表获取名称
   WHERE CODE.GROUP_TYPE = 'XXX_CODE'
3. 同时显示代码和名称
```

### 规则3：布尔值转换
```
IS_XXX 类字段（1/0）：
- 查询时：转换为 WHERE IS_XXX = 1/0
- 显示时：使用 CASE 转换为 是/否
```

### 规则4：精确匹配优先
```
⚠️ 重要：当用户指定了明确的实体名称时，必须使用精确匹配

❌ 错误：把完整名称拆分成多个 OR 条件
   WHERE NAME_ LIKE '%线控底盘%' OR NAME_ LIKE '%底盘%' OR NAME_ LIKE '%实训%'

✅ 正确：使用完整名称进行精确匹配
   WHERE NAME_ = '线控底盘实训室'
   或 WHERE NAME_ LIKE '%线控底盘实训室%'

判断标准：
- 用户输入的是完整实体名称（如"线控底盘实训室"、"李德声"）→ 精确匹配
- 用户输入的是描述性词汇（如"实训室"、"教师"）→ 模糊匹配
- 用户输入的是类别/范围（如"新能源汽车相关的"）→ 适当模糊匹配
```

### 规则5：ISTRUE有效性检查（必须）

⚠️ **极重要**：所有查询都必须检查 ISTRUE 字段，确保只查询有效数据

```
❌ 错误：没有检查ISTRUE
SELECT COUNT(*) FROM HQ_CODE_MAJOR

❌ 错误：只检查了主表的ISTRUE
SELECT COUNT(*) FROM HQ_CODE_MAJOR m WHERE m.ISTRUE = 1
AND NOT EXISTS (SELECT 1 FROM HQ_CODE_MAJOR_MAPPER mp WHERE mp.MAJOR_CODE = m.CODE_)

✅ 正确：所有表都检查ISTRUE
SELECT COUNT(*) FROM HQ_CODE_MAJOR m WHERE m.ISTRUE = 1
AND NOT EXISTS (
    SELECT 1 FROM HQ_CODE_MAJOR_MAPPER mp
    WHERE mp.MAJOR_CODE = m.CODE_ AND mp.ISTRUE = 1
)
```

**ISTRUE字段含义**：
- 1 = 有效/启用
- 0 = 无效/停用

**适用范围**：
- 几乎所有业务表都有ISTRUE字段
- 查询时必须加上 `ISTRUE = 1` 条件
- 多表关联时，每个表都要检查ISTRUE

**常见示例**：
```sql
-- 专业查询
WHERE m.ISTRUE = 1

-- 课程查询
WHERE c.ISTRUE = 1

-- 教研室查询
WHERE j.ISTRUE = 1

-- 部门查询
WHERE d.ISTRUE = 1
```

### 规则5：层级数据
```
部门/专业的层级：
- PID 字段存储上级ID
- 通过自关联查询上级名称
```

## Oracle 语法规范

### 大小写
```
✅ 表名和字段名大写：SELECT NAME_ FROM HQ_RS_TEA
✅ 字符串用单引号：WHERE NAME_ LIKE '%孙%'
❌ 字符串用双引号：WHERE NAME_ LIKE "%孙%"
```

### 分页
```
✅ FETCH FIRST n ROWS ONLY
✅ ROWNUM = 1 (单条)
❌ LIMIT n (MySQL语法)
```

### 日期
```
✅ SYSDATE
✅ TO_DATE('2024-01-01', 'YYYY-MM-DD')
✅ date BETWEEN ... AND ...
```

## 错误处理策略

### 表不存在
```
1. 检查拼写是否正确
2. 使用 list_tables 浏览所有表
3. 使用 RAG 搜索相似表名
```

### 字段不存在
```
1. 使用 describe_table 查看所有字段
2. 尝试字段名模糊匹配
3. 参考相似查询示例
```

### 结果为空
```
1. 检查筛选条件是否过严
2. 尝试使用 LIKE 扩大范围
3. 检查 ISTRUE 等标志位
4. 确认数据是否真实存在
```

## 批量问题处理规则

### 规则：批量问题必须逐个完整输出

当用户一次提出多个问题时（使用问号、句号、分号分隔）：

```
❌ 错误：只输出部分问题的结果
❌ 错误：省略SQL只显示结果
❌ 错误：合并多个问题的结果

✅ 正确：为每个问题都输出完整的格式
   问题1：
   ## 执行sql：
   SELECT ...
   ───────────────────────────
   - 查询结果
   ┌──────────┬───────────┐
   └──────────┴───────────┘

   问题2：
   ## 执行sql：
   SELECT ...
   ───────────────────────────
   - 查询结果
   ┌──────────┬───────────┐
   └──────────┴───────────┘
```

### 批量问题识别

识别用户输入中的多个问题：
- 包含多个问号 `?`
- 使用标点分隔：`。`、`；`、`? `
- 常见模式："A？B？C？" 或 "A，B，C"

### 批量问题处理流程

```
1. 识别输入中的多个问题
   │
   ▼
2. 使用 TodoWrite 工具创建任务列表
   │
   ▼
3. 逐个处理每个问题：
   - 标记当前问题为 in_progress
   - 完整输出：执行sql + 查询结果
   - 标记当前问题为 completed
   │
   ▼
4. 所有问题处理完毕
```

### 每个问题必须包含的输出元素

```markdown
## 问题 [序号/总数]：{用户问题原文}

**分析**：
- 查询类型：单表/多表/聚合
- 涉及表：表名

## 执行sql：

SELECT ...
FROM ...
WHERE ...
───────────────────────────
- 查询结果
   ┌──────────┬───────────┐
   │  字段1   │   值1     │
   └──────────┴───────────┘
   备注/说明

---
```

### 错误处理

- **某个查询失败**：明确输出错误信息，继续处理下一个问题
- **结果为空**：输出"未找到相关数据"，继续处理下一个问题
- **MCP服务异常**：输出"服务暂时不可用，请稍后重试"

## 优化技巧

### 技巧1：并行查询
```python
# 同时执行多个独立查询
list_tables() 和 describe_table() 可并行调用
```

### 技巧2：渐进式查询
```
复杂查询 → 先简单查询验证 → 逐步添加条件
```

### 技巧3：结果缓存
```
相同表结构可复用 describe_table 结果
```

### 技巧4：上下文利用
```
记住前面查询的表和字段，后续查询可直接使用
```

### 技巧5：批量问题进度跟踪
```
使用 TodoWrite 工具跟踪批量问题的处理进度
- 创建：识别到多个问题时创建任务列表
- 更新：每处理一个问题更新状态
- 完成：所有问题处理完毕清理列表
```

- [ ] SQL 语法正确（Oracle 规范）

- [ ] **ISTRUE检查：所有表都加了 ISTRUE = 1 条件**
- [ ] **精确匹配：用户指定完整名称时使用精确匹配，不要拆分关键词**
- [ ] **直接使用用户输入：WHERE条件使用名称而不是硬编码ID**
- [ ] 字符串使用单引号
- [ ] 代码字段关联了代码表
- [ ] 布尔值正确转换
- [ ] 结果格式化清晰
- [ ] 空结果有说明
